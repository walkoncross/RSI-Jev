# demo gallery 复跑记录：v6.1-VL 4B（MLX 8-bit）

**日期** 2026-10-15 · **运行者** 本机（Apple Silicon）· **结果文件** `/tmp/gallery_answers.json`（227 条）

用 `examples/gallery/` 那套带参考答案的题库，复跑了 v6.1-VL 4B 的 MLX 8-bit 量化版，目的是在 Apple GPU 上验证模型可用性与实际延迟，并和仓库里记录的 v4.0-VL-2B（bf16 / NVIDIA GB10）历史成绩做对照。

## 运行环境

| 项 | 值 |
|---|---|
| 硬件 | Apple Silicon，物理内存 17.2 GB，macOS（Darwin 25.6.0） |
| 模型 | `shgao/rsi-jev-v6.1-vl-4b-mlx-8bit`，8-bit affine / group 64，tower 权重 5.07 GB（源 bf16 为 8.41 GB） |
| 后端 | MLX 0.32.3，`mlx-gpu`（Metal），decoder heads fp32，vision tower bf16 |
| 服务 | `rsi-jev serve v6.1-vl-4b-mlx-8bit --backend mlx --host 127.0.0.1 --port 8000` |
| 运行方式 | `python examples/gallery/run.py --server http://127.0.0.1:8000 --out /tmp/gallery_answers.json` |
| 规模 | 143 个条目 / 89 张图 / 227 个问题，batch 1（与发布跑法一致） |

服务启动约 16 秒（模型加载 8 秒 + 两轮预热）。`RSIJEV_MLX_DELTA` 保持默认的 `chunk`；mlx-lm 的 Metal gated-delta kernel（`=kernel`）本章数据**未启用**，该开关的单独实测见文末附录（结论：本机无加速，保持默认）。

## 观察与解读

**1. 整体比两代前的参考高 17 题，增益集中在最大的两类。** road（124 题，占全库 55%）+10、clevr +6，合计 +16，占全部增益的 94%。hallucination（"这东西真的在吗"）两代都是满分，说明这一能力在 v4.0 时就已饱和。

**2. visa 是唯一低于参考的分类，但样本太小不足以立论。** 6 题里 3 对，"多错一题"就是 −16.7 个百分点。其中 `visa-candle_Data_Images_Anomaly_000` 以 **p=0.98 的高置信度答 A 而参考答案是 B**——工业零件缺陷检测这类任务，模型可能在看"零件是否完整"而非"是否符合该类别的正常形态"，但这个判断需要更多样本才能验证。

**3. 延迟由图像 token 数主导，与题目难度无关。** clevr 段（合成场景、图小）中位 996 ms，visa 段（工业大图）中位 7804 ms，相差 8 倍。所有请求都跑满 32 层（含图请求不做 adaptive 早退，符合 `docs/mac.md` 的说明）。因此"哪类题慢"实际反映的是"哪类图大"。

**4. 有个 69.5 秒的离群值，是冷启动而非稳态表现。** 最大值出现在 road 段靠前的请求。MLX 对**首次执行的代码路径**要做 kernel 编译，代价极高——这与本次排查 MLX 服务时发现的结论一致：路径必须在加载线程上先跑过一遍（见下文"运行前提"）。稳态中位数 2505 ms 才是该机器的真实水平。

**5. 三处高置信度错误值得单独看**（p ≥ 0.9 但判错）：

| 题目 | 模型答案 | 参考答案 |
|---|---|---|
| `ui-form-1/next` | pay · p=1.00 | card_number |
| `ui-form-2/next` | pay · p=0.94 | expiry |
| `visa-candle_..._Anomaly_000/inspection` | A · p=0.98 | B |

两条 `ui-form-*/next` 是同类失误：问"表单下一步该填哪一项"，模型直接跳到终点动作（pay），**没有跟踪表单的填写顺序**。这类"状态推进"问题与 road 段的 action 题（"前方有小孩该怎么做"）是同一个短板——模型能准确识别**看到了什么**（category 类问题几乎全对），但在**把观测转成下一步动作**时容易跳到最终目标。

## 方法学说明与局限

这个数字**不能当作严格基准**，模型、硬件、数值精度三个维度全都不同：

- **代次与规模**：v6.1-VL 4B vs v4.0-VL 2B，参数量翻倍且晚两代
- **数值精度**：本次是 **8-bit 量化**（affine g64），参考是 bf16。按 `docs/mac.md`，8-bit 与 bf16 答案一致率约 99.1–99.5%，即约每 200 题有 1 题会因量化翻转——在 227 题的规模上，量化本身就能造成 1–2 题的差异
- **硬件与框架**：Apple GPU + MLX vs NVIDIA GB10 + PyTorch。`docs/mac.md` 指出 MLX 与 PyTorch 在视觉 tower 上的算术有细微差异（图题的平均概率差 0.008，文本 0.004），接近的题可能翻转
- **`ref` 允许并列答案**：如 `ref=stop,slow_down` 表示两个可接受，判分按"命中任一即可"
- **`--compare` 的意义有限**：`expected.json` 存的是 v4.0-VL-2B 那次发布的答案，与本次不是同一模型，差异不等于错误

结论只应读作**趋势**：在这个题库上，v6.1-VL 4B 的 MLX 8-bit 版显著强于两代前的 2B 参考，且在 Apple GPU 上的稳态延迟足以支撑交互式使用（中位 2.5 秒，最快的合成图题 1 秒）。

## 运行前提：MLX 服务路径需要一处修复

本次能跑起来，依赖分支 `fix/mlx-serve-first-forward-thread` 对 `serve/server.py` 的一处修改。**未打该补丁时，MLX 后端每个请求都返回 500**：

```
RuntimeError: There is no Stream(cpu, 1) in current thread.
```

原因是 MLX 把模型加载时建立的东西绑定在**加载线程**的 stream 上，而 `serve_mlx` 的 `warm_up` 经 `GpuWorker` 派发到 worker 线程执行，于是第一次前向就落在"从未跑过该路径"的线程上（`Decider` 全程同线程，故不受影响）。修法是在建 worker 之前，先在加载线程上用 `make_scorer(s)` 跑一遍完整的 `warm_up`。

细粒度实测还确认：**粒度是代码路径而非精确形状**——加载线程跑过"短 state / 长 state / 图片"三条路径后，worker 线程可正常处理任意长度与问题数（实测未预热过的 40 遍、300 遍长度与 2 个、6 个问题全部通过）。

## 附：`RSIJEV_MLX_DELTA=kernel` 加速对比（结论：未采用）

`rsijev/mlx/text.py` 提供两个 gated-delta 实现：默认的 `chunk`（纯 MLX 分块递推），以及 `RSIJEV_MLX_DELTA=kernel`（改用 mlx-lm 的 Metal 专用 kernel，要求 Apple GPU + 已装 mlx-lm）。本文档其余部分的所有数据都是默认的 `chunk`。本机实测 **kernel 没有加速效果，因此保持默认**。

### 方法

分层抽样 94 题（road 41 / hallucination 23 / clevr 8 / charts 8 / ui 8 / visa 6），三次运行发送**完全相同的题、相同顺序**，每轮前 3 题预热后不计时。三次运行的机器状态并不对等：

| 运行 | 配置 | 机器状态 |
|---|---|---|
| `chunk`（首轮） | 默认 | **受污染**：紧跟在 227 题 gallery 全量跑之后，机器已热降频 |
| `kernel` | `=kernel` | 服务全新启动后的第一轮 |
| `chunk2`（复测） | 默认 | 服务全新启动后的第一轮 |

因此 **`kernel` 与 `chunk2` 才是可比的一对**；`chunk` 首轮的作用是量出同一配置两次运行之间的自身波动。

### 延迟对比（中位数，ms）

| 范围 | chunk 首轮 | chunk2 复测 | 自身波动 | kernel | kernel vs 复测 |
|---|---|---|---|---|---|
| **全部** | 3160 | **2449** | **−22.5%** | 2562 | **+4.6%** |
| road | 3544 | 2876 | −18.9% | 2571 | −10.6% |
| charts | 5067 | 3455 | −31.8% | 3817 | +10.5% |
| **clevr** | 1380 | 1341 | −2.8% | 1980 | **+47.6%** |
| hallucination | 1389 | 1181 | −15.0% | 1132 | −4.2% |
| ui | 4318 | 4119 | −4.6% | 4020 | −2.4% |
| visa | 8047 | 7423 | −7.8% | 7481 | +0.8% |

分布形状（全部 94 题）：

| 运行 | p25 | 中位 | p75 | p90 | p99 | 最大 | 均值 |
|---|---|---|---|---|---|---|---|
| chunk 首轮 | 1877 | 3160 | 5138 | 9315 | 50532 | 50532 | 4593 |
| chunk2 复测 | 1457 | 2449 | 3455 | 6418 | 11051 | 11051 | 2968 |
| kernel | 1786 | 2562 | 3910 | 6392 | **66480** | **66480** | 4459 |

### 三条判据

**1. "kernel 快 19%" 是时序假象。** 同一配置两次运行的中位就差 −22.5%（3160 → 2449），比 kernel 相对首轮的增益还大。与机器状态可比的复测相比，kernel 的中位反而 **+4.6%（更慢）**。

**2. 分布主体重合，差距全在尾部。** p90 几乎相同（chunk2 6418 vs kernel 6392），但 p99 差了 6 倍（11051 vs 66480）。kernel 那轮出现两个 58–66 秒的离群值，且都落在 token 数最高的一批题上：

| 题目 | tokens | chunk2 | kernel |
|---|---|---|---|
| `visa-chewinggum_..._Normal_487.JPG/inspection` | 1063 | 8065 ms | **66480 ms** |
| `visa-candle_..._Anomaly_000.JPG/inspection` | 1034 | — | **58644 ms** |
| `ui-ba-False/broke` | 1050 | 11051 ms | 21737 ms |

**3. clevr 变慢是可复现的。** 两轮对比中 clevr 都是 kernel 更慢（对首轮 +43.4%、对复测 +47.6%），方向一致、幅度近似，是唯一稳定的 kernel 劣势信号（同时也说明它的"增益"并不均匀地作用于各类输入）。

### 数值等价性（唯一通过的一项）

在可比的 `chunk2` 与 `kernel` 两轮之间，**94/94 题的首选答案完全相同**；概率最大差为 0.0003（中位）、0.0015（均值）、0.0072（p95）、**0.0270（最大）**。也就是说 `RSIJEV_MLX_DELTA=kernel` 确实守住了 `text.py` 承诺的"同一 contract"，不会改变输出——它的问题只是在这台机器上没有收益。

### 推测原因

mlx-lm 版本为 **0.31.3**，而 mlx 为 **0.32.3**，两者未对齐（mlx-lm 不在 `mlx` extra 的依赖列表里，所以升级 torch 时没有跟着升）。Metal kernel 是 mlx-lm 的内部实现，跨主版本后性能特征未必仍然成立。`rsijev/mlx/text.py:28` 对此的措辞是 "to be …"，即项目自身也未给出该开关的实测数字；本记录可视为在其上的补充：**在此机器 + 此版本组合下不成立**。

### 方法学提醒

本机的运行间波动足以制造出 20 个百分点的假增益（同一配置两次运行中位差 22.5%）。因此在这台机器上做任何性能 A/B，**必须交替或重复运行**；先后各跑一轮就下结论会得到错误答案——本次若不是补做了 `chunk2` 复测，就会得出"kernel 快 19%"的结论。
